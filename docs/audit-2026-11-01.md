# Lifecycle audit for v0.3.1-alpha.1

The public baseline is tag `v0.3.0-alpha.1`, commit
`03c1088c668f3c53c98a8d94f5f4752ada860cb2`. The corrected source identifies
itself as **0.3.1-alpha.1**. See the
[release list](https://github.com/Borregro4/mcp-warden/releases) for availability.
Publishing a release does not upgrade an existing installation automatically.

## Reproduced defects

- **Background Tasks:** the initial JSON-RPC result released a request lease
  even though the returned MCP Task was still working. With a 200 ms idle
  policy, a 900 ms synthetic worker completed directly but was killed through
  the public lightweight proxy. The correction conservatively retains
  task-bearing sessions; see [task lifecycle](task-lifecycle.md).
- **Gateway backpressure:** a backend emitted all 8 MiB of a notification burst
  behind a parent that never read stdout. The bridge's working set grew by
  8,757,248 bytes in that reproduction. Its internal queue and line reader were
  unbounded. The correction uses bounded data queues, bounded frame parsing,
  checked asynchronous writes and a separate disconnect signal. This is not a
  global RAM sandbox.
- **Blocked stdout:** the public lightweight proxy remained alive with its
  owned backend after client stdin EOF while a 256 KiB response blocked stdout.
  Both local transports now share bounded raw-pipe writing so their main loops
  can observe EOF and write deadlines. Final output remains ordered and is
  drained on ordinary backend EOF.
- **False partial timeout:** a complete newline-delimited frame waiting for
  queue capacity could retain the partial-message timer. Backpressure must not
  be treated as slow/incomplete protocol input.
- **CLI preflight:** `doctor` reported ready with required runtime files or a
  usable profile missing. It now checks required modules and the profile shape
  without launching a backend. It remains a preflight, not a successful tool
  call or guarantee that an arbitrary program can start.
- **Unicode configuration:** JSON ASCII surrogate escapes in generated Codex
  configuration are invalid TOML for non-BMP paths. Literal Unicode preserves
  those paths. Invalid profile selection also returns a fixed diagnostic
  instead of a raw `KeyError` traceback.

The missing `windows_detached_console` attribute corrected in the previous
local Nexo supplement was a local regression, not a defect in the public tag.
The existing local cleanup/frame-limit corrections are preserved separately
from these newly reproduced findings.

## Design choices and remaining boundaries

The existing Windows ownership and stdio machinery were retained. The review
also inspected [mcp-snooze's proxy](https://github.com/askmegit/mcp-snooze/blob/89f75aaff0972a5161ea1ca324240500889d38ae/internal/proxy/proxy.go)
and [lazy-mcp-wrapper](https://github.com/sleticalboy/lazy-mcp-wrapper). Neither
their existence nor earlier favorable benchmarks establishes complete task
lifetime handling or compatibility with a particular client. No new dependency
was added and no external implementation was copied for these corrections.

HTTP gateway expiry still closes the session and requires client reconnection.
The audited installed five-profile gateway used a 900-second idle policy;
the Nexo stdio profile used explicit stateless restart after 300 seconds.
Those are different policies. Converting stateful tools to stateless restart
requires a separate per-backend qualification. It is not a safe generic fix.

Earlier validation remains historical evidence. A passing existing suite did
not cover the defects above; regressions now exercise their observable effects.
The corrected branch passed **61 Node test entries and 108 Python tests** on
Windows, with no skipped tests or failures in the final run. The isolated real
Nexo check completed two read-only calls across clean idle/wake, revalidated
metadata, retained one proxy connection, preserved the shared service's
PID/creation identity, and removed both test-created processes on close.
It used zero model calls and zero mutating tool calls. These checks do not
amount to a fresh four-hour endurance run or a desktop GUI qualification.
No claim is made about faster model generation, whole-computer RAM savings,
full experimental Task support, or every desktop app/backend combination.
